8.2 Migration sketch (Phase 0 and Phase 3)

-- Phase 0: stop the data loss and make counts trustworthy
ALTER TABLE gst_notices
  ADD COLUMN portal_key text,
  ADD COLUMN first_seen_at timestamptz NOT NULL DEFAULT now(),
  ADD COLUMN last_seen_at  timestamptz NOT NULL DEFAULT now(),
  ADD COLUMN portal_hash text,
  ADD COLUMN deleted_at timestamptz,
  ADD COLUMN computed_due_date date;
UPDATE gst_notices SET portal_key = coalesce(reference_number, case_id, md5(coalesce(description,'')||coalesce(issue_date::text,'')));
CREATE UNIQUE INDEX uq_gst_notices_portal_key ON gst_notices (client_id, source, portal_key) WHERE deleted_at IS NULL;
-- extension: POST gst_notices?on_conflict=client_id,source,portal_key  Prefer: resolution=merge-duplicates
-- and PATCH deleted_at for keys no longer returned — never DELETE the client's rows.

-- Phase 3: matter layer (all additive; a minimal matter_deadlines table arrives in Phase 1)

CREATE TABLE matter_stage_history (...); CREATE TABLE matter_events (...);

Back-fill plan

A one-off script groups existing gst_notices rows into matters by case_id (the portal's ARN for case-linked rows) and, for rows without one, by (client_id, financial_year, category). Staff then confirm groupings from a "Suggested matters" review page rather than editing 1,060 rows by hand. LUT and DRC-03 acknowledgements are auto-closed in the same pass.
