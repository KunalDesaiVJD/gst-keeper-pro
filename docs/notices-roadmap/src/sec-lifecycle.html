7.1 The lifecycles the module must model

Each row in gst_notices today is a flat portal record. A litigation ERP treats a matter as the unit of work: one dispute that moves through statutory stages, each with its own form, deadline, document and owner. The table below is the reference the stage engine, the deadline calculator and the alert rules are built from. Statutory periods are stated as the app should default them; every deadline stays staff-editable because notices routinely specify a different date.

Position to confirm with the partner

Default periods above follow the Act and Rules as generally applied; the notice text always governs and officers routinely grant shorter or longer windows. The engine therefore stores a computed deadline and an overriding deadline separately, and every alert states which one it used. Treat the 3-month appeal default and pre-deposit percentages as configuration held in a litigation_rules table, not as constants in code, so a Finance Act change is a data edit.

7.2 Stage model

Stages are a single ordered enum per lifecycle so that ageing, MIS and alerts can compare like with like. A matter moves forward through matter_stage_history; it never edits its stage in place without a history row.

Captured→Triage→Awaiting client data→Reply drafting→Partner review→Filed / submitted→Hearing→Order received→Appeal decision→Appeal filed→Closed (dropped / paid / won / lost / partly)
  • Captured → Triage is automatic on sync. A notice that arrives with a demand or a short clock (DRC-01B/01C, REG-17, MOV-07, DRC-13/16/22) is auto-tagged High priority.
  • Closed requires a reason and, where relevant, the order number or DRC-03 ARN. LUT acknowledgements and DRC-03 acknowledgements are auto-closed by rule, which is what removes the 446 stale "open" rows the dashboard shows today.
  • Reopen is allowed (an order can be followed by an appeal) and is logged.
